# 마지막 특종 개발 기획

## 1. 개발 목표
- 정식 게임 제목은 **마지막 특종**으로 확정한다. 부제는 붙이지 않는다.
- 현재 정리된 스토리 구조를 실제 플레이 가능한 UE5 프로젝트로 구현한다.
- 목표는 **짧지만 밀도 높은 1회차 호러 경험**을 만드는 것이다.
- 권장 플레이타임은 **50~60분 MVP / 55~72분 확장형**으로 잡는다.

---

## 2. 개발 방향 요약

### 2-1. 게임 구조
- **현실 파트**: 3D
  - 신문사
  - 횡단보도 사고
  - 병실 엔딩
- **꿈/사이트 파트**: 3D + UI + 2D 연출 혼합
  - 괴담 사이트 탐색
  - 낙인 시나리오 3개
  - 추격 세트피스 1개

### 2-2. 개발 핵심
- 플레이 볼륨을 크게 벌리지 않고, **챕터 단위로 확실한 경험을 주는 구조**로 간다.
- 시스템은 최소 공통 기반을 만들고, 미니게임은 그 위에 얹는 방식으로 구현한다.
- 연출은 되도록 **2D 일러스트 + UI + 카메라 연출 + 사운드**로 해결한다.
- **미니게임은 최후반 제작**으로 두고, 먼저 전체 진행 구조 / 사이트 / 연출 기반을 완성한다.

---

## 3. 현재 repo 기준으로 보이는 구현 상태

### 3-1. 이미 있는 것으로 보이는 것
- 로비/모니터 상호작용
- 모니터 UI 및 사이트형 화면 전환
- 윈도우/커서/패널형 UI 구조
- 기본 입력 처리
- 로비 이동 포인트 기반 상호작용
- 일부 데이터 테이블 / 스트링 테이블 구조

### 3-2. 아직 본격 구현이 필요한 것
- 스토리 진행 상태 관리
- 챕터 전환 구조
- 괴담 사이트 실제 게임 진행 흐름
- 낙인 획득/저장/연출 처리
- 미니게임 4종
- 병실 엔딩 UX
- 공포 연출 이벤트 시스템

### 3-3. 감사 기준 재사용 가능 기반
- **로비/모니터/컴퓨터 상호작용**은 이미 재사용 가치가 높음
- **사이트/윈도우형 UI 구조**는 기존 코드 확장으로 가는 것이 유리함
- **SaveGame 플러그인**은 존재하지만 프로젝트 진행 데이터는 아직 얹히지 않음
- **InteractionSystem / ItemCore / CustomUI**는 기반으로 활용 가능
- `StateTree`, `GameplayStateTree` 는 의존성만 있고 현재 실제 사용 코드는 없음

### 3-4. 감사 기준 주의점
- `TRACE_ERROR` 는 에디터에서 크래시를 유발하는 공격적인 정책
- `RulesHorrorDeveloperSettings` 는 사실상 비어 있음
- 전역 게임 진행 관리자(Game Flow)가 없음
- 자동화 테스트가 없음
- `RulesPlugin` 은 현재 실사용 흔적이 거의 없음

## 4. MVP 기준 플레이 구조

| 챕터 | 내용 | 형태 | 목표 |
|---|---|---|---|
| 1 | 신문사 / 전화 / 사고 | 3D 스토리 | 도입 |
| 2 | 규칙괴담 PC방 | 미니게임 | 첫 낙인 |
| 3 | 무궁화 꽃이 피었습니다 변형 | 미니게임 | 두 번째 낙인 |
| 4 | 칠흙 숲 탈출 | 미니게임 | 세 번째 낙인 |
| 5 | 창문 추락 원혼 추격 | 추격 세트피스 | 공포 피크 |
| 6 | 병실 엔딩 | 연출 + 선택지 UX | 마무리 |

---

## 4-1. 감사 반영 개발 원칙
- 새 기능은 **기존 로비/모니터/사이트 구조를 확장**하는 방식으로 붙인다.
- 미니게임보다 먼저 **전역 진행 상태 / 챕터 흐름 / 허브 구조**를 만든다.
- `StateTree` 는 현재 필요하지 않으므로 도입 보류
- UI 폴리시는 후순위, **플레이 흐름이 이어지는지**를 먼저 확인
- 병실 엔딩 선택지는 **분기 UX가 아니라 무력감 UX** 로 구현

## 5. 코어 시스템 정의

## 5-1. 게임 진행 상태 시스템
### 목적
- 현재 챕터, 시나리오, 낙인 획득 여부, 엔딩 진입 조건을 관리한다.

### 필요 기능
- 현재 진행 챕터 저장
- 낙인 3개 획득 여부 저장
- 미니게임 클리어 상태 저장
- 특정 연출 재생 여부 저장
- 병실 엔딩 진입 조건 판정

### 구현 형태 제안
- `GameInstance` 또는 별도 `Subsystem` 기반 전역 진행 관리자
- 세이브 연동 가능한 구조

---

## 5-2. 괴담 사이트 진행 시스템
### 목적
- 메인 꿈 공간에서 사이트 UI를 통해 시나리오를 선택/진행/복귀하게 한다.

### 필요 기능
- 사이트 메인 화면
- 시나리오 진입 버튼 상태 제어
- 클리어 후 낙인 반영
- 다음 시나리오 해금
- 마지막 추격전 강제 진입

### 구현 형태 제안
- 기존 모니터/사이트 UI 구조 재사용
- 사이트용 상태머신 추가

---

## 5-3. 챕터 전환 시스템
### 목적
- 현실/꿈/미니게임/엔딩 간 전환을 자연스럽게 연결한다.

### 필요 기능
- 로딩/페이드
- 챕터 시작/종료 이벤트
- 카메라 전환
- 사운드 전환
- UI 락/언락

### 구현 형태 제안
- 공통 `ChapterFlowManager`
- 시퀀스/블루프린트 연출과 연결

---

## 5-4. 공포 연출 이벤트 시스템
### 목적
- 사이트 진행도에 따라 점진적으로 공포 요소를 강화한다.

### 필요 기능
- 출현 타이밍 제어
- 화면 노이즈/글리치
- 사운드 점프
- 귀신 실루엣/짧은 출현
- 카메라 강제 회전/시야 고정

### 구현 형태 제안
- 데이터 기반 이벤트 테이블
- 챕터/낙인 조건별 재생

---

## 5-5. 미니게임 공통 프레임워크
### 목적
- 서로 다른 미니게임이지만 공통적으로 쓰는 진입/실패/재시도/클리어 처리를 통일한다.

### 필요 기능
- 시작 연출
- 규칙 설명 UI
- 실패 처리
- 재도전
- 클리어 처리
- 보상(낙인) 연동

### 구현 형태 제안
- `MiniGameBase` 계층
- 공통 HUD / 공통 상태 enum

---

## 5-6. 병실 엔딩 UX 시스템
### 목적
- 플레이어에게 선택하고 있다는 감각은 주되, 실제로는 말이 나오지 않는 무력감을 전달한다.

### 필요 기능
- 대사 선택지 표시
- 선택 입력 허용
- 선택 후 무반응 혹은 쉰 숨소리/내면 텍스트 처리
- 카메라 고정 상태 유지
- 최종 연출 트리거

### 구현 형태 제안
- 일반 선택지 UI 재사용 가능
- 결과는 분기 없이 동일
- 선택지는 몰입 장치, 게임 분기 수단이 아님

## 8-1. 최우선 개발 기능 추천

### 1순위: 전역 게임 진행 상태 시스템
가장 먼저 만들어야 한다.

#### 이유
- 현재 코드에는 **게임 전체 진행을 관리하는 중심축이 없음**
- 낙인, 챕터, 시나리오, 엔딩 조건이 전부 여기에 걸림
- 이게 없으면 사이트 허브도, 병실 엔딩도, 미니게임 진입도 다 임시 처리로 흩어짐

#### 최소 요구사항
- 현재 챕터
- 현재 허브 단계
- 낙인 획득 여부 3개
- 현재 진입 가능한 시나리오
- 병실 엔딩 진입 가능 여부
- 저장/불러오기 연계

#### 구현 추천
- `GameInstanceSubsystem` 또는 프로젝트 전용 `GameFlowManager`

### 2순위: 챕터 전환 / 씬 흐름 시스템

#### 이유
- 지금 프로젝트는 **씬 단위 경험의 연결**이 핵심임
- 신문사 → 사고 → 허브 → 엔딩 더미만 이어져도 프로토타입 검증이 가능
- 미니게임이 없더라도 전체 리듬을 먼저 볼 수 있음

#### 최소 요구사항
- 시작 씬 진입
- 사고 씬 전환
- 허브 씬 진입/복귀
- 병실 엔딩 진입
- 페이드/사운드/카메라 전환

### 3순위: 꿈속 허브 + 괴담 사이트 진행 구조

#### 이유
- 네 게임의 실제 중심 허브임
- 기존 모니터/사이트 코드 재사용 가치가 가장 높음
- 미니게임을 나중에 붙여도 허브는 먼저 검증 가능

#### 최소 요구사항
- 사이트 메인 진입
- 시나리오 슬롯 3개
- 더미 진입 버튼
- 낙인 슬롯 반영
- 마지막 단계에서 창문 추격전 진입 가능 구조

---

### 4순위: 병실 엔딩 UX

#### 이유
- 엔딩은 이 프로젝트의 인상과 톤을 확정하는 구간
- 구현 난이도 대비 효과가 큼
- 미니게임보다 먼저 완성해도 전체 방향성을 검증할 수 있음

#### 최소 요구사항
- 고정 시점
- 대화 청취
- 말하기 선택지
- 선택 후 무반응
- 최종 공포 연출 트리거

#### 이유

- 허브/사고/병실/추격전 전부에 공통 재사용 가능

#### 최소 요구사항
- 글리치
- 시야 고정
- 깜빡임
- 짧은 귀신 출현
- 사운드 점프

## 10. 개발 리스크

### 10-1. 가장 큰 리스크
- 미니게임 4개가 각각 따로 노는 문제
- 사이트/꿈/현실 전환이 복잡해지는 문제
- 추격전 구현 비용 증가
- 공포 연출이 리소스 부족으로 약해지는 문제

### 10-2. 대응
- 공통 프레임워크 먼저 구축
- 미니게임은 “짧고 선명하게”
- 2D 일러스트와 UI 연출 적극 활용
- 미니게임은 후반에 붙이고, 먼저 전역 흐름부터 완성
- 숲 탈출만 상대적으로 길게, 나머지는 밀도 중심으로 구성
