# 마지막 특종 개발 기획

## 문서 역할

이 문서는 `마지막 특종`의 **개발 우선순위 정리 문서**다.
스토리/연출의 세부 서사 기준은 `스토리기획.md`를 따르고, 이 문서는 아래 두 가지만 빠르게 판단할 수 있게 정리한다.

- 지금 **이미 구현된 기능**이 무엇인가
- 지금 **다음으로 구현해야 할 기능**이 무엇인가

정렬 기준은 **중요도 순**이다.

---

## 1. 개발 목표

- `Scene_Intro` → `CH01_S01` → 허브/사이트 → 낙인 3개 → 추격 → 병실 엔딩까지 이어지는 **완주 가능한 호러 게임 루프**를 만든다.
- 미니게임 개별 완성보다 먼저 **전체 진행 흐름이 끊기지 않는 구조**를 만든다.
- 기존에 만든 **StoryFlow / 모니터 UI / 사이트 UI / 상호작용 시스템**을 최대한 재사용한다.
- 최종 목표 플레이타임은 **2시간 반**이다. 시간은 전체 흐름이 이어진 뒤 미니게임 구체화(6단계)에서 채운다. 배분은 `챕터-씬-기획서.md` 4-2.

### 확정된 기획 결정 (2026-11-05)
- 괴담 사이트명: `i-wish` (아이위시, `www.i-wish.co.kr`)
- 꿈속 허브: 밤의 사무실 (`L_Office`를 복사한 `L_DreamOffice`)
- 제보 전화: 퇴근길 횡단보도에서 받고, 회사로 되돌아가다 사고 (`L_Street`)
- 인터루드 2개: `CH03_S01`(인터루드 1), `CH03_S05`(인터루드 2)
- 씬별 맵 표: `챕터-씬-기획서.md` 4-1

---

## 2. 현재 상태 한 줄 요약

현재 프로젝트는

- **인트로/새 게임/이어하기와 전역 진행 상태(낙인·시나리오·엔딩 조건) 저장**이 있고 (1단계),
- **`CH01_S01` ~ `CH02_S03` 본편 더미 흐름**이 StoryFlow로 이어지며 (2단계),
- **모니터/사이트/컴퓨터 상호작용 기반**이 있지만,
- **i-wish 사이트 화면과 해금 표시, `CH02_S04` 이후 Scene, 미니게임, 엔딩 UX**가 아직 없다.

즉, **뼈대와 앞부분 흐름은 있음 / 사이트 진행 구조와 이후 콘텐츠 연결이 아직 부족함** 상태다.

## 3. 중요도 순 기능 정리

## 3-1. 최우선: 전역 진행 상태 + 저장/이어하기

### 왜 최우선인가
이 기능이 없으면 낙인, 시나리오 해금, 엔딩 조건, 이어하기가 모두 따로 놀게 된다.
현재 게임 전체를 하나로 묶는 핵심이다.

### 이미 구현된 기능
- `StoryFlow` 기반으로 인트로와 본편 시작 Scene 진입 가능
- `URulesHorrorGameInstance`에서 새 게임 / 이어하기 시작 가능
- `URulesHorrorSaveGame`에 `FStoryFlowRef` 저장 가능
- 이어하기 시 저장된 StoryFlow 위치 재시작 가능
- (2026-11-05) 낙인 3개, 시나리오 해금/클리어, 병실 엔딩 조건, 현재 챕터 저장 (`ERulesHorrorProgressFlag`, Save Key는 `챕터-씬-기획서.md` 3장)
- (2026-11-05) Shot 노드 `IsCheckpoint`로 이어하기 위치 저장, `Shot_SetProgress`로 진행 플래그 저장, `Branch_CheckProgress`로 조건 분기
- (2026-11-05) `URulesHorrorProgressSubsystem`에서 진행 상태 조회/변경 알림. 이어하기 시 저장된 진행 상태와 체크포인트 복원
- (2026-11-05) `CH01_S01` 첫 Shot을 체크포인트로 지정

### 추가 구현이 필요한 기능
- 허브/사이트 UI가 진행 상태를 표시하도록 연결 (3단계)
- 새로 만드는 Scene에 체크포인트 / `Shot_SetProgress` 배치 (`CH01_S01` ~ `CH02_S04`는 2단계에서 배치함)

### 완료 기준
- 새 게임 / 이어하기 / 재시작이 안정적으로 동작한다.
- 낙인, 시나리오 진행, 엔딩 조건이 저장되고 복원된다.

---

## 3-2. 매우 중요: StoryFlow 본편 확장

### 왜 중요한가
지금 구조상 게임 진행의 중심은 StoryFlow다.
본편 Scene이 늘어나지 않으면 게임은 인트로와 시작점 이상으로 확장되지 못한다.

### 이미 구현된 기능
- StoryFlow Subsystem
- Scene / Shot / Branch 구조
- Intro 흐름
- `CH01_S01` ~ `CH02_S03` 더미 연결, `CH02_S04` 자리표시 (2026-11-05, 2단계)
- 공통 Shot 최소판: Fade, Dialogue, Set Input Lock, Set Objective, Wait, Wait Story Event, Set Interactable, Computer Action, Teleport Player (+ Set Progress)
- 조사 오브젝트(`StoryInspectable`), 도달 트리거(`StoryTriggerVolume`)

### 추가 구현이 필요한 기능
- `CH02_S04` 이후 본편 Scene 추가
- 공포 연출용 공통 Shot (카메라 강제 전환, 글리치, 사운드)
- 낙인/조건 분기용 Branch 추가
- 현실 → 허브 → 사이트 → 추격 → 병실까지 Scene 연결

### 완료 기준
- 미니게임이 더미여도 전체 챕터 흐름이 StoryFlow로 끝까지 이어진다.

---

## 3-3. 매우 중요: 허브 + 괴담 사이트 진행 구조

### 왜 중요한가
이 게임의 반복 루프는 허브와 사이트를 중심으로 돌아간다.
플레이어가 다음 시나리오를 선택하고, 낙인을 확인하고, 다시 복귀하는 구조가 필요하다.

### 이미 구현된 기능
- 모니터 UI 진입 구조
- 브라우저형 멀티 윈도우 UI
- 사이트 목록 / 상세 구조
- DataTable 기반 스토리 항목 조회
- 사이트에서 맵/시나리오 진입 가능한 기본 구조
- (2026-11-05, 2단계) 기존 닉네임 입력 화면을 닫으면 `CH02_S03` 사이트 가입으로, 사이트에서 괴담 입장을 누르면 첫 시나리오 선택으로 StoryFlow에 알림

### 추가 구현이 필요한 기능
- `i-wish` 사이트 화면 (낡은 개인 홈페이지 느낌, 낙인 3칸)
- 시나리오 해금/잠금 반영
- 클리어 상태 표시
- 낙인 상태 표시
- 허브(밤의 사무실) 변화 반영
- 사이트에서 직접 맵 오픈하는 임시 흐름을 StoryFlow 중심 구조와 정리 (시나리오 선택 → StoryFlow Scene 전환)

### 완료 기준
- 허브에서 사이트 진입
- 사이트에서 현재 가능한 시나리오만 선택
- 클리어 후 다음 시나리오 해금
- 낙인 상태가 UI에 반영

---

## 3-4. 중요: 현실 파트 상호작용 / 디제틱 컴퓨터 UX

### 왜 중요한가
이 기반은 이미 강하고, 게임의 분위기와 차별점이기도 하다.
새로 만드는 것보다 확장하는 편이 훨씬 효율적이다.

### 이미 구현된 기능
- 컴퓨터 Actor 상호작용
- 이동 포인트 기반 컴퓨터 접근
- 모니터 전원 On/Off
- 월드 표면 기반 UI 상호작용
- 모니터 내부 커서 / 입력 보정
- 창 열기/닫기/이동/리사이즈
- (2026-11-05, 2단계) 조사 오브젝트(`StoryInspectable`), 도달 트리거, 컴퓨터 사용 완료를 스토리 이벤트로 보내 StoryFlow 진행 조건(`Wait Story Event`)으로 사용. 구간별로 조사 오브젝트·컴퓨터 상호작용을 켜고 끔(`Set Interactable`)

### 추가 구현이 필요한 기능
- 허브용 조사 오브젝트 확대
- 현실 파트 정보 노출 오브젝트 추가 (문서 UI 등 2단계의 대사 상자보다 나은 표시)

### 완료 기준
- 현실 파트와 허브 파트의 필수 상호작용이 모두 StoryFlow 진행과 연결된다.

---

## 3-5. 중요: 공포 연출 공통 프레임워크

### 왜 중요한가
본편 Scene 수가 늘수록 공포 연출을 매번 따로 만들면 유지보수가 어려워진다.
공통 Shot 형태로 묶는 게 효율적이다.

### 이미 구현된 기능
- StoryFlow Shot 구조 자체
- 일부 공통 Shot 기반 존재

### 추가 구현이 필요한 기능
- 자막 표시
- 입력 잠금/해제
- 특정 상호작용 대기
- 글리치 / 노이즈 / 사운드 연출
- 강제 시선 / 카메라 제어
- 낙인 획득 처리
- 저장 갱신 처리

### 완료 기준
- 자주 쓰는 연출이 재사용 가능한 Shot으로 정리된다.

참고: 페이드, 자막/대사, 입력 잠금/해제, 상호작용 대기, 목표 표시는 2단계 Scene 제작에 바로 필요하므로 2단계에서 최소판을 먼저 만든다. 4단계는 이를 다듬고 글리치·사운드·카메라 연출을 더한다.

---

## 3-6. 중요: 병실 엔딩 UX

### 왜 중요한가
이 게임의 최종 인상이 병실 엔딩에서 결정된다.
스토리상 마무리와 감정적 타격을 담당한다.

### 이미 구현된 기능
- 병실 엔딩 자체의 기획 방향 존재
- StoryFlow로 엔딩 Scene 연결 가능한 구조 존재

### 추가 구현이 필요한 기능
- 조작 불능 상태 표현
- 선택지는 있지만 결과는 바뀌지 않는 무력감 UX
- 진실 공개 연출
- 마지막 심판 연출

### 완료 기준
- 병실 엔딩이 단순 텍스트가 아니라 플레이 체험으로 완성된다.

## 3-7. 후순위지만 필수: 미니게임 4종

미니게임은 중요하지만, **전체 진행 구조가 먼저**다.
개별 미니게임은 전체 루프가 이어진 뒤 순차적으로 붙인다.

### 우선순위
1. 규칙괴담 PC방
2. 무궁화 꽃이 피었습니다 변형
3. 칠흙 숲 탈출
4. 창문 추락 원혼 추격

### 이미 구현된 기능
- 시나리오를 담을 구조는 있음
- 상호작용 / UI / StoryFlow 기반 있음

### 추가 구현이 필요한 기능
- 규칙 시스템
- 실패/재도전 흐름
- 클리어 조건
- 낙인 획득 연결
- 공포 이벤트 삽입

### 완료 기준
- 최소 더미 버전이라도 StoryFlow 안에서 진입/클리어/복귀가 된다.

## 5. MVP 완료 기준

아래가 되면 MVP로 본다.

- 인트로에서 새 게임 / 이어하기 선택 가능
- `CH01_S01`부터 게임 시작 가능
- 허브와 사이트를 통해 시나리오 선택 가능
- 낙인 3개 획득 가능
- 세 시나리오 클리어 후 추격 파트 진입 가능
- 병실 엔딩까지 완주 가능
- 저장/이어하기가 전체 진행 상태를 복원 가능

## 6. 가장 큰 리스크

### 1) 콘텐츠보다 시스템이 늦게 정리되는 경우
Scene/Shot는 늘어나는데 저장/분기 규칙이 늦으면 나중에 다 엉킨다.

### 2) 미니게임을 너무 빨리 파고드는 경우
전체 루프가 없는 상태에서 미니게임만 먼저 만들면 프로젝트가 분산된다.

### 3) 연출을 전부 개별 구현하는 경우
공통 Shot 없이 각 Scene마다 따로 만들면 유지보수가 무거워진다.
